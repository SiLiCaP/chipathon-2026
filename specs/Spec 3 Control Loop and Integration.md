# Spec 3: Control Loop and Integration

Oct 17, 2026 · @A

## Your job

You own control, sequencing and the final wiring. The other four people hand you finished blocks, and you build `ntt_core` around them so all four modes run correctly.

- **In scope:** the op latch and job state machine, all counters, the ROM and γ select, the operand registers, the multiplexers, the bypass delay line, the loop-back path, cancel and reset, and wiring every block together.
- **Out of scope:** the inside of the multiplier, adders, packer and input capture, and the host side.
- **You hold the interface table.** Anyone who wants to change a port asks you first, and you update all five specs.

You are the one person who sees every block, so three things are yours to publish early: the interface table, the per-mode schedule and the output delay table. The section "What you publish to the other four, and when" lists them.

## Who owns which block

You build `ntt_core` and everything inside it except the arithmetic blocks, which you instantiate. The block diagram is on the architecture page listed in the shared rules.

| Block | Module | Owner |
| --- | --- | --- |
| Multiplier | `modq_mul` | Multiplier |
| Add/subtract, one for Pre ± and one for Post ± | `modq_addsub` | Adders |
| Running sums for basemul, two of them | `modq_acc` | Adders |
| Pin capture | `io_in_capture` | I/O |

| Host harness, reference model, vectors | not RTL | Pi |
| Everything else in `ntt_core` | `ntt_core` | You |

Inside `ntt_core` you build: the op latch and job FSM, the counters, `zeta_rom` with the ζ / γ select and the scale constant 304, the operand registers (b and a, or g1 f1 g0 f0), the B-input select, the Pre and Post pass-through muxes, the bypass delay line, the loop-back path, the result pairing for scale, and the flush.

`ntt_core` is the boundary with the I/O owner. Its ports are fixed as follows.

| Port | Dir | Width | Meaning |
| --- | --- | --- | --- |
| `clk`, `rst_n` | in | 1 each | Clock and synchronous reset |
| `coeff_q` | in | 12 | Captured coefficient, from `io_in_capture` |
| `valid_q` | in | 1 | Captured valid |
| `sof_q` | in | 1 | High only when valid and sof were both high |
| `op_q` | in | 2 | Captured op. Read only when `sof_q` is high |
| `r0` | out | 12 | First result of a pair |
| `r1` | out | 12 | Second result of a pair |
| `pair_valid` | out | 1 | High for one clock when `r0` and `r1` are valid |
| `flush` | out | 1 | High for one clock when a job is cancelled. Goes to `io_out_pack` |

## Op latch, modes and job lifecycle

A job starts on the clock where `valid_q` and `sof_q` are both high. You latch `op_q` on that clock and run that mode until its last result.

- **Idle.** Wait for `valid_q` and `sof_q`. Coefficients that arrive with `valid_q` but no earlier sof are ignored.
- **Start.** On the sof clock, latch the op, clear every counter, and take this coefficient as the first input of the job.
- **Running.** Take a coefficient on every clock where `valid_q` is high, in the order the mode defines. Clocks with `valid_q` low are skipped and change no counter.
- **End.** After the last pair is emitted the job ends by itself and you return to idle. Extra coefficients after the last expected one are ignored until the next sof.
- **Cancel.** A new sof while running cancels the job. See the cancel section.

You know each job's length from the mode. The host never sends it.

| op | Mode | Inputs | Result pairs out |
| --- | --- | --- | --- |
| 00 | Forward NTT | 1792 | 896 |
| 01 | Inverse NTT | 1792 | 896 |
| 10 | Basemul | 512 | 128 |
| 11 | Scale | 256 | 128 |

## Counters, ROM index and constants

You pick every constant. The host only sends coefficients.

**ROM.** `zeta_rom.v` holds the scaled table ROM′\[k\] = 17^BitRev7(k) × 2197⁻¹ mod 3329 for k = 0..127, where 2197⁻¹ = 944. The multiplier returns 2197 × a × b (three K-RED rounds, see the Multiplier spec), so with a stored ζ′ the product b × ζ′ comes out as b × ζ. It was generated by script and has never been compiled. Compile it, lint it, and compare all 128 entries with the Pi owner's scaled table.

**Forward NTT.** The ROM index starts at 1 and goes up by 1 after every block. A block is `len` butterflies that share one ζ. There are 127 blocks and 896 butterflies.

| len | Blocks | Butterflies per block | ROM indices |
| --- | --- | --- | --- |
| 128 | 1 | 128 | 1 |
| 64 | 2 | 64 | 2 to 3 |
| 32 | 4 | 32 | 4 to 7 |
| 16 | 8 | 16 | 8 to 15 |
| 8 | 16 | 8 | 16 to 31 |
| 4 | 32 | 4 | 32 to 63 |
| 2 | 64 | 2 | 64 to 127 |

**Inverse NTT.** The same table read from the bottom up. `len` goes 2, 4, ..., 128, and the ROM index starts at 127 and goes down by 1 after every block, ending at 1. For len = 2 it covers 127 down to 64, and for len = 128 it is 1.

**Basemul.** A piece counter runs 0..127. With j = i >> 1, the scaled γ′ for piece i is ROM′\[64 + j\] when i is even and 3329 minus that entry when i is odd. One subtractor makes the negative, and no ROM′ entry is 0. The loop-back multiplies m1 by γ′, so m2 = 2197 × m1 × γ′ = m1 × γ.

**Scale.** The constant is 304 = 3303 × 2197⁻² mod 3329 (128 × 3303 = 127 × 3329 + 1), fixed in wiring. The ROM is idle. In the full flow its input already carries one factor of 2197 from basemul, so the multiplier's own 2197 leaves a net factor of 3303.

Checks from the reference model (scaled table): ROM′\[0\] = 944, ROM′\[1\] = 966, ROM′\[2\] = 2021, ROM′\[3\] = 2188, ROM′\[64\] = 2732 and ROM′\[127\] = 2686. γ′ for pieces 0, 1, 2, 3 is 2732, 597, 3106, 223, and for pieces 126, 127 it is 2686, 643. For reference, the unscaled table has ROM\[1\] = 1729, ROM\[64\] = 17, ROM\[127\] = 2154.

## What the pins show because of K-RED

The multiplier returns 2197 × the product. Your scaled constants cancel the factor in both NTT modes, so those are plain. Basemul keeps it, and scale removes it.

| Mode | What the output bytes carry |
| --- | --- |
| Forward NTT | The plain FIPS 203 result |
| Inverse NTT | The plain FIPS 203 result for plain input. For basemul output as input it gives 2197 × the plain result (the transform is linear) |
| Basemul | 2197 × the plain basemul, mod 3329 |
| Scale | c × 3303 × 2197⁻¹ mod 3329 |

So the host flow forward, forward, basemul, inverse, scale gives the correct final polynomial. Scale on its own is not a plain × 3303.

Worked values for your tests:

- Basemul with f0 = 5, f1 = 7, g0 = 11, g1 = 13 and γ = 17 (plain answer c0 = 1602, c1 = 142): the products are m1 = 187, m2 = 3179, m3 = 991, m4 = 2987, m5 = 2719, so the pins give c0 = 841 and c1 = 2377.
- Scale input 2197 gives 3303. Scale input 3259 gives 316. Scale input 1132 gives 26 (inputs that carry 2197, as basemul output does, come out as plain × 3303).
- Forward butterfly with b = 2000, a = 1000, ζ = 1729: t = 2498, a′ = 169, b′ = 1831.

Tell the Pi owner if you change any of this, because the reference model, the vector files and the demo depend on it.

## Per-mode schedules

Every mode repeats on a fixed period: 3 clocks for forward, inverse and scale, and 15 for basemul. The multiplier starts at most once every 3 clocks.

The tables below are a proposed starting point. You own the final cadence. Publish it as `schedule.md`. Offsets are clocks from the unit's first input, and idle clocks have `valid` low.

**Forward NTT, one butterfly (period 3)**

| Offset | Host sends | Chip does |
| --- | --- | --- |
| 0 | b | Capture b |
| 1 | a | Start b × ζ right away, because only b is multiplied. Hold a |
| 2 | idle | Multiplier digit clocks |
| t arrives | none | Post ±: a + t and a − t. Pair out: r0 = a', r1 = b' |

**Inverse NTT, one butterfly (period 3)**

| Offset | Host sends | Chip does |
| --- | --- | --- |
| 0 | b | Capture b |
| 1 | a | Capture a |
| 2 | idle | Pre ±: a + b and b − a. Start (b − a) × ζ. Delay a + b |
| product arrives | none | Pair out: r0 = a + b (delayed), r1 = (b − a) × ζ |

The inverse needs both inputs before the multiplier can start, which is why its output delay is larger than forward's.

**Basemul, one piece (period 15)**

| Offset | Host sends | Chip does |
| --- | --- | --- |
| 0 | g1 | Capture g1 |
| 1 | f1 | Capture f1 |
| 2 | g0 | Start pass 1: f1 × g1 = m1 |
| 3 | f0 | Capture f0 |
| 4 to 14 | idle | Passes 2 to 5, each 3 clocks after the last: m1 × γ = m2 (loop-back), f0 × g0 = m3, f0 × g1 = m4, f1 × g0 = m5 |
| after pass 5 | none | c0 = m2 + m3 and c1 = m4 + m5. Pair out: r0 = c0, r1 = c1 |

f1 and g1 come first because f1 × g1 × γ is the only chain of two multiplications.

**Scale (one coefficient per 3 clocks)**

c arrives and c × 304 starts (net c × 3303 in the full flow, see the K-RED section). Two results make one pair, so one pair is emitted every 6 clocks. You do the pairing: hold the first result as r0, and pulse `pair_valid` when the second result is ready as r1.

Streaming job lengths with this cadence: forward and inverse 896 butterflies × 3 = 2688 clocks, basemul 128 × 15 = 1920, scale 256 × 3 = 768. These exclude the host's waits between NTT layers.

## Latency and alignment

Results must reach the Post ± stage together, so you delay the shorter lane to match the longer one.

- **Forward.** t = b × ζ arrives L\_mult clocks after the multiplier starts. The bypass value a waits in a delay line of the same length before Post ±.
- **Inverse.** The bypass lane carries a + b. The product (b − a) × ζ arrives L\_mult clocks after the start. Delay a + b to match.
- **Basemul.** Pass 2 needs the output of pass 1. If L\_mult is more than 3, run an independent pass (such as f0 × g0) in between. The 15 clocks per piece still hold.
- **Output delay D.** The first byte of a pair leaves D clocks after the pair's first input. The handoff assumed D = 5 forward and 7 inverse. The real value is the sum of the stage latencies below plus your own register stages.

| Stage | Owner | Reports |
| --- | --- | --- |
| Input capture | I/O | 1 clock |
| Multiplier | Multiplier | L\_mult = 3 (pipelined, one result per clock) |
| Add/subtract | Adders | 0 or 1 clock per instance |
| Output packer | I/O | 1 clock |
| Your registers, muxes and delay lines | You | Your own count |

Compute D for each mode and send the numbers to the Pi owner as `host_timing.md`. If D for forward comes out above 5, that is fine. Only a constants file on the host changes. With L\_mult = 3 the measured values are D = 6 forward, 7 inverse, 20 basemul and 9 scale. Forward is one clock over the handoff because the multiplier takes b from a register, one clock after it arrives.

Also check that `pair_valid` is never closer than 3 clocks apart, and add that as an assertion.

## Reset, cancel and flush

- **Reset.** `rst_n` low clears the counters, the operand register, the delay lines and the op latch. The chip is then idle and ready for a start of frame.
- **Start of frame.** A pin word with `sof` and `valid` both high starts a job. Latch `op` on that clock only, reset the counters, and drop any job still in progress.
- **Cancel.** A new start of frame always wins. Send `flush` to the output packer in the same clock so stale bytes are dropped.
- **Idle.** With `valid` low and no job running, every output is 0x00 and nothing toggles needlessly.
- **Unused op.** All four op codes are used, so there is no illegal code. Check the table anyway.

## Tests

- **Whole-core, per mode.** Run `ntt_core` with the other four blocks against the Pi owner's reference model: one forward layer, one inverse layer, basemul of two random polynomials, and scale.
- **Full flow.** Forward NTT of f and g, basemul, inverse NTT, scale. The result must equal schoolbook negacyclic multiplication mod 3329.
- **Output delay.** Measure D for each mode from the waveform. It must match `host_timing.md`.
- **Rates.** Check clocks per butterfly (3), per basemul piece (15) and per scale coefficient (3).
- **Reset and cancel.** Reset mid-job. Start a new frame mid-job. Both must leave no stale bytes.

## Risks to watch

- **Multiplier latency too long.** Basemul pass 2 depends on pass 1. If L\_mult is more than 3, interleave an independent pass.
- **Output delay differs from the handoff.** D of 5 and 7 are assumptions. Send the real numbers to the Pi owner early.
- **Area.** The ROM is 128 × 12 bits. If it does not fit, use the γ symmetry to store only 64 entries for basemul and derive the rest.
- **Layer-by-layer round trips.** The host re-sends data for every NTT layer because the chip stores nothing. Check the host counts against the timing table.

## Shared rules for all five specs

- **One chip, one clock.** Everything runs on `clk`. Reset is `rst_n`, active low. Synchronous logic only, no latches, no generated clocks.
- **Numbers.** Every coefficient is 12 bits, unsigned, always in 0..3328 on every port.
- **Ports are frozen.** You hold the interface table. Other owners tell you before changing a port, and you tell them.
- **Latency is reported.** Collect every block's latency from its README and publish `host_timing.md`.
- **Reference.** The Pi owner's Python model is the source of truth.
- **Sharing.** These docs are private. Share them with your teammates.
